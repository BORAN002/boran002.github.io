Agent Harness：从工具循环到可验证的任务执行

2026.10.20
目录

一个模型已经能够搜索仓库、修改文件、调用测试，为什么仍会在长任务里反复读同一段代码、忘记尚未解决的问题，或者在测试没有跑完时宣布完成？

讨论 Agent Harness，我更关心这些具体的断点。模型输出到真实任务结果之间，还有一层系统负责选择信息、执行动作、保存进度和检查证据。本文以代码 Agent 为主要例子，整理截至 2026 年 10 月 20 日阅读的一手论文与工程资料。文中的设计建议是综合归纳，实验结果则注明对应条件。

TL;DR

  • Harness 决定模型能力如何进入任务。 它组织每一步输入、动作执行和反馈，也管理预算、权限、停止与恢复。
  • 当前上下文只是任务状态的一部分。 压缩后的摘要适合帮助模型继续推理；文件、事件日志和验证记录承担可追溯的事实。
  • 完成必须对应证据。 “补丁已生成”“测试命令已启动”“目标行为已验证”是三个不同的状态。
  • 复杂度本身不构成进步。 固定工作流、单 Agent 循环和多 Agent 分工都应在相同任务与预算下比较；换模型之后，也要重新检验原有设计。

一、Harness 的边界在哪里

这个术语尚没有统一边界。LangChain 采用较宽的定义，将模型之外的代码、配置与执行逻辑纳入 Harness；Anthropic 的 Managed Agents 架构则把 session、harness 和 sandbox 分成独立组件，harness 更接近负责模型调用与工具路由的执行循环。[1] [2]

本文采用一个便于讨论的工作定义：Agent Harness 是围绕模型、组织任务执行的运行控制层。 它可以调用外部存储和沙箱，不要求把这些基础设施都实现在同一个进程里。

概念 主要回答的问题
Model 给定当前信息，下一步输出什么？
Agent loop 模型动作和环境反馈如何形成循环？
Harness 循环依据什么运行，如何验证、停止和恢复？
Framework / SDK 用哪些可复用组件实现这套系统？
Environment / sandbox 动作在哪里执行，能访问哪些资源？

这些角色在具体产品里可能重叠。一个框架可以自带默认 Harness，一个 Harness 也可以直接用少量代码实现。判断它是否完整，应当看任务执行时承担了哪些责任，而不是安装了多少组件。

ReAct 展示了一个关键起点：推理、动作和观察交织发生，环境返回的信息进入下一步决策。它研究的是这种交互范式的价值，没有覆盖生产系统需要的持久状态、权限管理和崩溃恢复。[3] 从这个起点继续追问，才会进入 Harness 的问题：上一轮工具超时了怎么办？窗口放不下历史了怎么办？模型说“完成”之后，谁来检查？

二、相关文献到底证明了什么

下表按问题组织文献，同时列出机制与证据边界。

工作 值得关注的机制 证据边界
ReAct，2022 / ICLR 2023 [3] 将推理、动作和观察交织在同一轨迹里 支持交互式决策，不等于完整运行系统
SWE-agent，2024 [4] 为模型设计搜索、查看、编辑与错误反馈接口，即 ACI 有同模型接口消融；结论依赖当时模型与软件修复任务
Agentless，2024 [5] 用程序固定定位、修复、验证的阶段，让模型完成局部判断 说明较少自主控制也能有效；不代表固定工作流普遍占优
Confucius Code Agent，2025，本文读 v6 [6] 分层工作记忆、结构化压缩、跨会话笔记和模块化工具 应区分同模型消融与跨系统主榜，避免把模型差异归给架构
Meta-Harness，2026，v1 [7] 外层 Agent 读取候选代码、评分和执行轨迹，搜索新的 Harness 不同实验采用不同划分；编码实验的搜索与最终评测共用 89 道题
Code as Agent Harness，2026，v1 [8] 从接口、机制、多 Agent 协调三个层次整理代码的作用 属于综述提出的组织视角，不能当作某种架构最优的实验证明
AI Harness Engineering，2026，v1 [9] 把任务状态、验证、权限、可观察性等整理成运行时责任 四级配置各执行一次小型登录任务，只用于展示方法，不支持总体性能优势

SWE-agent 提供了一个比“某系统拿到高分”更具体的观察。在 GPT-4 Turbo、SWE-bench Lite 的接口消融中，带 lint 检查的编辑器达到 18.0% resolved，去掉 lint 后为 15.0%；完整保留最近五次观察、将更早观察各压成一行时为 18.0%，使用完整历史为 15.0%。[4] 这组结果支持的是：动作接口和反馈呈现会改变结果，更多历史未必更好。 它不能直接变成所有新模型都该“只留五轮”的配置规则。

Agentless 则提醒我们注意另一个方向：当任务可以稳定拆解时，把阶段顺序交给程序，可能比让模型反复决定流程更合适。[5] 我会因此把“简单工作流 + 必要反馈”作为基线，再检查哪些步骤确实需要自主探索。

Meta-Harness 把设计对象进一步向外推了一层：模型权重保持固定，优化的是围绕模型运行的程序。它让外层 Agent 按需读取历史候选的原始轨迹，诊断失败后修改 Harness。[7] 这里有一个值得区分的细节：保留完整经验供检索，与把完整经验塞进每次上下文，是两种设计。 同时，其 TerminalBench-2 结果来自在同一组任务上搜索和评测，适合说明特定基准上的优化能力，不能单独证明对新编码任务的泛化。

三、长任务中的四个关键边界

3.1 当前上下文与持久状态

当前上下文服务于这一次模型调用；持久状态需要在模型调用结束、上下文压缩甚至进程重启之后仍然成立。

Anthropic 的 context engineering 文章讨论了按需检索、压缩、外部笔记和子任务上下文隔离。[10] Confucius 则把分层记忆、结构化压缩与跨会话 Markdown 笔记放进代码 Agent 的实现。[6] 它们共同提示了一种组织方式：把长历史留在外部，让模型读当前需要的部分。

对于一个修复任务，我会区分三类材料：

  • 任务记录：目标、约束、尚未解决的问题、当前停在哪一步。
  • 执行证据：代码版本、工具参数、退出码、测试报告、产物路径。
  • 工作摘要：当前假设、已排除的方向、下一步建议。

前两类应尽可能从实际执行中记录，摘要可以由模型整理。若摘要写着“测试通过”，而测试报告显示超时，应以报告为准。压缩也不应把“尚未验证的推测”改写成“已经确认的事实”。

因此，好的压缩结果不必复述全部历史，但应让下一轮知道：现在要做什么、有哪些证据、哪些问题仍未确定，以及到哪里找回细节。

3.2 工具调用与有效动作

工具返回成功，能证明的范围取决于接口约定：可能只是请求已受理，也可能是操作已执行；它仍不自动证明任务目标已经满足。

例如，执行测试时应记录命令、工作目录、代码版本、退出状态与日志位置。输出过长，可以保留摘要和原始日志路径；若测试超时，就把“超时”明确反馈给下一轮。

权限也应在执行边界检查。对一个只获准修改本地代码的任务，模型生成了部署命令，并不会自动产生部署授权。这里需要可执行的控制逻辑；仅在提示词中写一条规则，无法替代工具侧的检查。

从这个角度看，《Code as Agent Harness》对代码的关注很有启发：程序、配置、测试和运行产物让部分推理与动作变得可执行、可检查、可保存。[8] 但能运行的代码仍可能执行错误目标，验证必须回到任务本身。

3.3 模型停止与任务完成

一个常见断点是把“模型已经输出最终回答”直接映射为“任务成功”。实际需要分别记录产物状态与退出原因：

状态 应当依据什么判断
已验证完成 与目标对应的检查通过，证据属于当前产物版本
产物已生成，验证未完成 有结果，但测试缺失、超时或环境不具备条件
等待外部条件 缺少必要权限、输入或依赖，需要保留进度
预算耗尽或运行失败 达到限制，或基础设施故障阻止继续执行

这些记录可以同时存在：例如产物已生成、验证未完成，退出原因是预算耗尽。它们不应被压缩成一个模糊的 done。

Anthropic 的长任务案例让初始化阶段建立功能清单、启动脚本与进度文件，后续会话按项推进并进行端到端检查。[11] 这类工程实践的价值在于把“还剩什么”和“怎样算通过”显式写出来。不过，它主要讨论全栈应用，不能直接作为所有任务成功率提升的统计证据。

验证器本身也有边界。单元测试只能覆盖写出的断言，浏览器检查只能覆盖走过的路径，另一个模型担任 evaluator 也可能遗漏问题。对于代码修复，更合理的证据组合是：原问题复现、修复后行为检查、相关回归测试，以及必要的人工审查。若某项没有完成，就保留这个缺口。

3.4 从中断恢复与重新执行

Anthropic Managed Agents 将 session 定义为持久事件日志，把 Harness 与执行沙箱解耦，使执行循环能够依靠外部记录恢复。[2] 这种分离有助于跨进程延续任务，但恢复仍需确认环境当前发生了什么。

设想一次工具调用已经发出，网络连接却在返回前断开。如果操作只是读文件，重新读取通常容易处理；如果操作已经发布了一个版本，直接重试就可能重复发布。没有收到结果，并不意味着动作没有发生。

我的工程取舍是：记录动作身份与预期影响，对支持幂等键的接口使用幂等键，同一逻辑动作重试时复用原键；对结果未知的外部写操作，先查询状态，再决定是否重试。恢复点至少应包含任务进度、最后确认的动作、待核实的动作和当前产物版本。事件日志提供恢复依据，不能自动保证所有副作用都只发生一次。

四、把这些责任落到一个最小任务里

以“修复 CSV 导入时空行导致的崩溃”为例。下面是一个说明性的执行方案，不是本文实际跑出的实验。

第一步，定义可检查的目标。 记录触发崩溃的输入，同时确认空行应被跳过还是报错，以及已有合法输入应保持什么行为。若需求没有规定，就先保留这个问题，不能把模型猜测当作验收标准。

第二步，保存基线。 在修改前复现错误，记录代码版本和执行命令。如果环境缺依赖而无法复现，应区分环境失败与目标缺陷。

第三步，进行小步修改。 模型读取相关函数与调用位置，提出补丁；工具将补丁应用到已确认的工作区，并返回真实结果。每次修改都更新产物版本，旧测试结果不再自动适用于新版本。

第四步，验证目标和回归。 对当前版本运行复现用例与相关测试。失败时，把具体输入、错误位置和日志送回循环；通过时保存报告，而不只留下一句自然语言总结。

第五步，形成可继续的交接。 记录改了什么、验证了什么、还有什么未确认。如果预算在第四步耗尽，应记录“验证未完成”和退出原因；下次先核对产物版本与未结束的操作，再从验证阶段继续。

这套流程可以由一个 Agent 完成。只有当执行轨迹显示某些工作确实适合独立上下文，例如需要并行分析两个互不依赖的模块，才值得加入子 Agent。分工需要支付额外调用和信息交接的成本。

我会先保留以下最小实现，再根据失败样本增加组件：

任务目标与验收条件
        ↓
读取状态 → 选择上下文 → 模型提出下一步
        ↑                    ↓
保存观察 ← 执行动作 ← 检查参数、权限与预算
        ↓
检查当前产物
        ├─ 条件满足：保存证据并结束
        ├─ 尚未满足：反馈失败，继续迭代
        └─ 无法继续：保存原因与恢复点

预算限制需要覆盖工具调用、验证和重试，并配套执行超时与取消机制。否则，一个看似有轮数上限的循环，仍可能在工具内部无限等待。

五、怎样判断 Harness 真的更有效

“换了 Harness，分数变高了”只是观察。要判断改动是否有效，首先要固定比较条件：模型与版本、任务集合、环境、可用工具，以及时间和费用上限。采样设置与每题尝试次数也应记录。若故意放宽预算，就同时报告新增成本。

我会采用下面的评估方式：

  1. 保留简单基线。 从直接工具循环或固定工作流开始，每次只加入一个待验证的机制，例如上下文压缩、失败重试或额外 evaluator。
  2. 按失败原因检查轨迹。 区分定位错误、修改错误、工具故障、状态丢失和过早停止。观察指标变化是否与组件预期解决的问题一致。
  3. 将开发任务与最终测试任务分开。 用开发集调整 Harness，在未参与调参的任务上检查迁移效果；跨仓库或时间划分也应明确说明。
  4. 在有随机性的任务上重复运行。 报告重复次数与波动，不把一次幸运轨迹当作稳定能力。

需要同时看的指标也不只有最终成功率：

指标 为什么需要它
经验证的任务成功率 统计最终结果，而不是模型自报完成
费用与耗时分布 判断收益是否依赖更多计算，关注慢任务的尾部
错误完成率 检查系统是否把未通过或未验证的产物标成成功
中断后的恢复表现 通过受控中断，检查进度丢失、重复动作与恢复成本
人工介入情况 区分补充必要需求、批准操作和接手修复系统失败

这些指标是本文建议的评估维度，不是已经统一的行业标准。对不同任务，还需要写清分母和判定方式。例如“恢复成功率”的分母应是实际注入中断的任务，而不应混入从未发生中断的运行。

评估器还要和被评估的执行过程保持边界。Agent 可以知道公开需求和允许使用的测试，但不应在调试 Harness 时读到隐藏测试答案或参考补丁。否则，系统可能学会适配评估材料，却没有获得相应的任务能力。

读完这些工作，我会把 Harness 看作一个需要持续检验的工程对象。随着模型和任务变化，曾经有用的机制也可能需要缩小或移除。最终关心的仍然是：在给定资源下，任务是否留下了可检查的结果，以及失败后能否解释和继续。
